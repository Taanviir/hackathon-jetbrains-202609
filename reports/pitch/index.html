The problem

An agent's first minutes are a scavenger hunt

grep "retry"read Client.ktgrep "backoff" read Config.ktglob **/*Retry*read RetryPolicy.kt grep "delay"read ClientTest.ktedit

Each hop is a full LLM round-trip: tokens in, tokens out, seconds gone. On a 2,000-file project the agent reads files one at a time to find the three that matter.

Real Koog tasks: Claude Code averaged 13 turns per task.

The IDE already knows every file. The agent is re-discovering the project through a keyhole, one tool call at a time.
The insight

Use a model that decides, not one that writes

Jev

Judges, never writes

TypeSafe's System One model answers typed questions with calibrated probabilities. No text generation, so it's fast.

Batching

60 files per call

One call asks "does this task need file f07?" about 60 files at once, and many calls run in parallel.

Cost

$0.042 / M tokens

Scoring every file in a large project costs cents, so we can afford to ask about all of them.

Let Jev do the looking. Leave the writing to the LLM.

An LLM is the wrong tool for asking the same question 2,000 times. Jev is built for exactly that.
How it works

One parallel sweep over the whole project

01

Sketch

Every file becomes a ~300-token outline: path, declarations, doc lines.

2,206 files · 1.4 s
02

Pass 1

Jev scores all sketches. BM25 keyword search ranks full text alongside.

60 files / call
03

Pass 2

The top 60 of each go back to Jev with their full source.

6 files / call
04

Fuse

Jev and BM25 count equally. Weight picked on dev tasks only.

equal weight
05

Compare

One Jev choice over the top 10: which file must be edited?

+0.4 s

Result: the top 10–20 files, tests flagged, with roles like edit, test and example.

Jev alone on sketches actually loses to keyword search. The win comes from re-ranking on full source and fusing with BM25. We measured that, which is why the pipeline looks like this.
Where it lives

Inside the IDE, and inside your agent

Tool window

Type a task

See ranked files with roles and scores. Pin or drop files, then copy the prompt or ask an LLM.

MCP tool

pack_context

Registered on IntelliJ's built-in MCP server, so any MCP agent can call it.

Claude Code hook

Zero effort

Runs on every prompt and injects the packed files before Claude sees the request.

Offered only as a tool, Claude Code never called it. So we put the context where the agent can't miss it.

This is the "wow" bit. The developer doesn't change how they work. They type a prompt as usual, and the agent already knows where to look.

What we measured honestly

Where it doesn't win, yet

  • Jev alone loses. Scoring sketches alone gets recall@10 of 0.39 against 0.46 for keywords. Full-source re-ranking plus fusion is what wins.
  • An LLM picks the top 5 better (0.61 vs 0.52) but takes 29 s, not 1 s. At 10 files they tie.
  • Wall-clock time didn't drop inside Claude Code. It saves turns and cost, not minutes.
  • New codebase, frozen settings (JetBrains/Exposed): recall@5 +0.10, significant. recall@10 +0.07, not significant.
  • A local model (Laya) did not beat keyword search on our benchmark, so keywords remain the free offline option.
We'd rather show you the misses than hide them. Every number here is in the public eval report.
