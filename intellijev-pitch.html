IntelliJev

An IntelliJ plugin for agent efficiency. We put a decision model in the agent's hot path, so the expensive model is only called when it has earned the call.

IntelliJevThe framing

Why this, why now

Jevons paradox, running inside your IDE

The name is not a pun we reverse-engineered. It is the actual problem.

The models got better

Every generation is smarter, so we hand them more. The scope of what we ask an agent to do has grown faster than the models have got cheaper.

So we spend more, on less

A frontier model now burns reasoning tokens deciding which file to open, whether a step finished, and whether a one-line question deserves a one-line answer.

The decisions are not the work

None of those choices produce a line of code. They are glances, and we are paying essay prices for them.

The correction  a model that cannot write prose, answering the glances, at a fraction of a cent and a fraction of a second02
IntelliJevThe problem

Real problems, not invented ones

We asked each other what actually slows us down

Three developers on this team, three answers, all of them the same shape.

Tanvir

I cannot follow my own agents

Multiple sessions running at once, each generating more output than anyone can read. Keeping track of what each one is doing, and holding that in your head while you work, becomes the bottleneck.

Mahad

Rate limits land mid-task

The limit hits halfway through, the thread is lost, and you restart rather than resume. Nothing tells you what was finished and what was not.

Abdul Aziz

I pay frontier prices for trivia

A throwaway question asked inside a long session, because starting a new chat loses the context. The dumbest question in the room costs the most.

What they share  none of these are reasoning problems. They are all cheap judgements that nothing cheap is making.03
IntelliJevThe model

Jev · TypeSafe System One

Unstructured state in, typed decisions out

Jev cannot emit a string. That constraint is the whole design: it decides, it never writes.

Latency70–500msend to end, per decision
Input$0.042per million tokens
OutputFreetoo cheap to meter
Choice255options per decision

What a call looks like

POST /api/alpha/decisions

{ "model": "jev-latest",
  "state":  "<the code and its context>",
  "questions": {
    "would_edit": { "type": "noul",
      "instructions": "this task requires
       changing this file" } } }

→ { "would_edit": { "noul": 0.94 } }

What that buys us

  • Calibrated. A 0.94 means something, so thresholds and budgets are real rather than guessed.
  • Type safe. It cannot hallucinate a filename or invent an option that was not offered.
  • Cheap enough to be everywhere. Scoring an entire repository costs cents, so we ask about every candidate instead of guessing at a few.

IntelliJevFind

Feature 02

You fixed one path. Which others had the same bug?

The same business rule, written three times by three people under three names. No search finds all of them.

The scenario

Expired coupon validation

You fix expired-coupon validation in normal checkout. IntelliJev flags express checkout and subscription renewal, where equivalent validation still lets expired coupons through.

  • Why grep fails. The paths have different names and different implementations. Nothing was copied, so nothing matches.
  • Jev's job. Answer one narrow question against every candidate: does this function enforce the same eligibility rule? Then rank what comes back.
  • The demo. Fix one checkout path, discover a forgotten path, reproduce the original bug there live.
Ranked 0.96

ExpressCheckout.applyPromo()

Same rule, same gap. No shared code with the path you fixed.

Ranked 0.91

SubscriptionRenewal.validate()

Expiry checked against the wrong clock.

The hard part

Intentional, or overlooked?

Some differences are deliberate. We show the code and let the developer judge, rather than auto-fixing.

Why it needs Jev  one narrow judgement, asked of every function in the repository, for cents08
IntelliJevSteer

Features 03 to 05

Three decisions made before the model is ever called

All three are invisible when they work, which is the point.

Tool and skill finder

Pick from three, not forty

Every tool definition in the prompt costs tokens and attention. Jev skims what is available, shortlists the plausible few, and the model chooses from those.

Shorter prompt, faster choice, fewer wrong turns.

Model router

Not every question deserves the frontier

Ask something trivial mid-session and you pay frontier prices for it. Jev rates the difficulty and routes to the cheapest model that will answer.

You select several models once. The plugin handles the rest.

Message context

This question does not belong here

Jev checks whether your prompt continues this thread. If not, it opens beside it rather than dragging the whole history along.

Highlight any part of a reply to open a bubble that carries only that fragment.

Why it needs Jev  a routing decision that costs an LLM call has already lost the saving it was making09
IntelliJevWatch

Features 06 to 08

Knowing what your agents just did to your codebase

The output problem. Agents generate more than anyone can read, and none of it is summarised cheaply.

Turn status

A dot on every turn

The way CI marks a commit. Each agent turn carries a status, the diff it produced, and whether its tests held. Scroll back and read the thread at a glance instead of rereading it.

Rate limit rescue

Resume, do not restart

Jev marks each step complete or not as the run proceeds. When the limit lands, you come back to what was finished and what remains, rather than to nothing.

Sessions and endings

Three agents, one codebase

Parallel sessions are impossible to follow. Jev classifies what each is doing and what it touched, and writes the end-of-run report: what changed, what was wasted.

Why it needs Jev  summarising every step of every session with an LLM costs more than the run it is summarising10
IntelliJevHonesty check

The test we hold ourselves to

Take Jev out. Does the feature still work?

If an LLM can do it, just slower, it is not a Jev feature. We rated our own eight.

The first five sit in the hot path, where a 70 to 500 millisecond decision is the difference between a feature and a demo nobody would leave switched on. The last three are honest about being conveniences that Jev makes affordable rather than possible.

The evaluation

Git history is the answer key

  • Take 50 real commits. The message is the task. The files that commit touched are the correct answer.
  • Measure recall at ten. IntelliJev against grep, against embeddings, on identical tasks.
  • Chart it. The data already exists in the repository, so this costs us an afternoon.

Almost nobody brings a baseline to a hackathon. We intend to.

What we need from you

What is settled, what is open, what we are asking

We would rather be told now which features to drop than find out on stage.

Settled

The architecture

Jev decides in the hot path, the LLM writes on demand, PSI supplies structure for free. Every feature here is that one shape, which is why eight ideas fit in one plugin.

Open

Three unknowns

  • How many questions fit in one call. All of our batching maths depends on it.
  • Real latency under parallel load.
  • Whether signatures alone carry enough signal, or we need a second pass on full text.
Asking
  • Is context exploration the right flagship, or is bug fix propagation the better story?
  • Does a measured before-and-after count for more than a wider feature set?
  • How much JetBrains integration do you want to see by the deadline?
